# 动态凑批性能实测（2026-10-14）

## 范围与硬件

开发机 8× NVIDIA L40，nvidia-smi 每卡 46068 MiB；GPU 0 原有约 1119 MiB 的其他进程保持不动。
PyTorch 2.14.1+cu130；Diffusers 固定提交 916a5791ed5f29d966200d2eee53f06862ec4434。
模型使用已下载的 Qwen-Image-2.1-Turbo，官方 Turbo 调度与 CFG=1。
全部测试在 Linux 执行，合成输入/输出留在开发机 .run/tuning；代码通过 Git push/pull 同步。

单卡表格是独立参考图片、不同长度提示词的 1024 局部生成，通常一轮热身加三次计时取中位数。
compile/offload/FP16 为两次热计时；单独 VAE slicing 测试只有一次热计时。
为缩短总测试时间，部分独立参数测试在不同 GPU 同时运行，共享 CPU/磁盘；
小幅差异不能直接当作严格的单参数因果收益。用户真实照片尚未提供，不是画质验收数据。

## 正确性

- 适配层 batch=1 与固定版本原始 pipeline 的输出像素完全一致（MAE=0）。
- batch=2 各图片与对应单图输出的 MAE 约 2.17、1.00；与另一张单图输出约 15.66、15.41。
  这是独立条件对应关系检查，BF16 批维度导致的数值变化不要求逐像素一致。
- padding attention 与 PyTorch 带 mask 的 SDPA 数值对照通过。
- 本地 33 项测试通过，Ruff 检查通过；测试覆盖在途图片计数、OOM 拆批、单图失败隔离、透明通道及全部 8 种 EXIF 方向。
- 保存时检查原文件宽高；EXIF 旋转图先正向处理再反变换，保留存储尺寸和观看方向。

| reduce-overhead | — | — | — | CUDA Graph 输出被后续调用覆盖错误 |

已知失败的组合在生产启动配置校验阶段拒绝，避免加载完模型才发现不兼容。
默认关闭 compile；自动检测会产生变化的裁剪形状，固定形状的热调用收益不能直接外推。
确有固定尺寸大批量场景可用 --compile --compile-mode default，再测显存和全流程时间。

## 参数选择原则

- 完整启动脚本显式启用 batch bucketing、OOM 拆批、KV、VAE tiling/slicing、TF32。
  所有 bool 的裸参数默认仍为 false。
- 默认全 8 卡、每卡一个模型、最大 batch 2、候选窗口 4、在途 32、加载并行 8、BF16、SDPA、GPU 常驻、CPU 线程 1。
- OOM 后记住该尺寸的较小 batch 上限，避免同一 worker 重复大批 OOM。
- 检测 1280、生成 1024、context=0.6、feather=12、seed=42 保持为质量基线。
  检测分辨率会单独比较；没有真实样本时不宣称已找到画质最优值。
- host/port/路径/下载源是部署配置；prompt/seed/region/remove_logo 是任务语义，
  不能靠跳过水印、漏检、降低质量或已有文件跳过来制造性能提升。
- 复现命令与完整参数见 [启动指南](startup-and-tuning.md)；全部测试脚本在 scripts/benchmark-*.py。
